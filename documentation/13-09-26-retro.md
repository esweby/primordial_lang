# 13/09/26 Retrospective

While Primordial is a 'for fun' project, it would be beneficial to take a look back on the last six months of work and quickly cover the amount of work that has been done, the achievements, failures, and potential solutions that present themselves. This isn't an exhaustive look, by any means, but it should provide a good outlet to keep the language moving forwards and meeting the goals I'd like to achieve.

## Where is Primordial?

As of writing this, the following language features have been implemented

- structs
  - struct properties
  - struct literals
  - struct methods
  - struct access rules
- arrays and slices
- maps
- functions
  - function expressions
  - function literals
- if
  - if as expressions
- for loop
  - infinite
  - for while
  - for with condition declaration
  - range based for

### Lexer

The lexer introduced by Monkey is a common pattern used in compilers for multiple languages (see Go, Rust, V8, and more) and is simple enough to follow and expand upon. It made sense to continue with this pattern going forward and not overcomplicate every step as I expand the language. The major addition to this is including line, column, and span tracking, which improves error handling from the lexer up.

There is currently no need to improve the lexer and try to fix something that isn't broken.

### Token

The earliest point I deviated from Monkey was moving away from Monkey's string-based token system and towards using iota. This is both leaner in memory (a 16x reduction for the token type field, from string to iota) and faster in execution than Monkey's original system. The second change is how names are retrieved: instead of using the name directly, we use a lookup table indexed by token type, which is a reasonable trade off of a one-off memory allocation.

The most beneficial change is including the positional and span information from the lexer directly into the token itself. Again, this is a big win in terms of debugging myself or when leveraging AI for quicker debugging sessions.

The biggest future wins are likely to do with performance here as I could serve to slim the system down, but this would be a far future effort and unlikely to be a concern in the near future.

### Parser

The parser used by Monkey is largely unchanged except in terms of organisational structure and how much of the Primordial language it covers. In terms of organisation I tried out file-based segmentation and have found that to be a double-edged sword. While it is nice to jump into a file associated with a particular language feature, it has also led to the folder becoming overwhelmed with both implementation and associated test files.

The extension of the language and addition of more detailed error handling are big wins for the project. A lot of the initial language features are now implemented and are easy to adjust should the need arise. On the whole, this has been a big win for the project, but I will be making the following changes in the future.

- Reducing the files to associated types, e.g. statements, expressions, and maybe statementExpressions
- Reviewing error handling in more detail and ensuring that I can move more detail into the error
- Implementing error recovery
- Adjusting the priority system to be broader (perhaps levels of 10) to future-proof the language against any new operations

These changes would make a big difference to the quality of the parser and usability of the language.

### Semantic

The single biggest change to the project is the addition of the semantic analyzer. The semantic analyzer takes a fully formed ast and then parses through it to achieve two major goals:

- Enforce type safety and error on any violations
- Infer types that are unknown

This system works largely like the parser and makes use of powerful utilities from the types system to compare and contrast what has been picked up.

One of the major sticking points of the semantic system is that it has become overloaded with responsibilities. When I made the decision to infer values at this step it also brought some (not all) of integer management, which magnifies the complexity of the system altogether.

The primary solution is to implement an inference layer between the parser and the semantic analyzer. This would be a layer with a single responsibility, confirming or inferring types from context or analysis. This would dramatically reduce the complexity of the semantic system and make implementing features within the environment and ensuring type safety far simpler.

### Types

The types system was a big goal for Primordial. By giving the user a real type system to work with I hand them the power to make their programs safer and behave predictably. The system has clearly defined types, along with their metadata. The initial framework for builtins is there for use by the semantic layer and the evaluator to perform checks on user code.

The initial framework of members has also been implemented and will lead to maps, arrays, and slices becoming more powerful as I give them methods that make sense within the context of Primordial.

While it is still early in the types system, it is already clear that the integer system needs to live here. Currently, analysis takes place across the semantic and evaluator layers. By bringing a specific set of methods into the types package, behaviour between the semantic and evaluator layers becomes consistent and more predictable. With a sensible API it also allows me to fine-tune the area without breaking the contract with the other systems.

### Evaluator

The evaluator has been lifted from Monkey and the same pattern has been followed. My initial thought was to not spend too much time in here as would eventually be invalidating the Evaluator as we work towards the compiler. In the long run it seems wiser to improve the architecture of the Evaluator towards the interface implementation used in the parser and semantic layers.

### REPL

Much like the evaluator, I have not looked into the REPL all that much, preferring to delegate to AI for quicker results as I focus on the language structure. This currently allows me to run files from the command line, which is a very cool experience as the language starts to have that early feeling of 'being real'.

```
./pri run examples/server/server.pri
```

## What's next?

On the whole this has been a very productive start to this project and I am immensely proud of how far I have come. I have highlighted some big wins in this retro but have decided to hone in on some shorter wins that take advantage of six months of hard work. The next phase of work will include the following short term goals:

- Tidy up the evaluator to use an interface
- Implement some very basic but powerful examples of real world projects

My longer term goals will be the following:

- Addition of the new layer between the parser and the semantic
- Adding the integer system to the type system and hammering down a well defined contract
